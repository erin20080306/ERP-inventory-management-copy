# Decimal／浮點誤差盤點

## 結論

目前資料庫金額欄位多為 Prisma `Decimal`，但應用層大量轉為 JavaScript `number` 後再計算。現有 `Math.round` 可把多數新台幣整數交易收斂到元，但無法完整保證折扣分攤、分批出貨、稅額與大量加總不出現一元殘差。

本文件先盤點與固定規則，不在本批直接改變既有會計結果；避免已出帳資料因四捨五入規則突然改變。

## P0：優先處理

### 銷售／採購總額

`src/lib/documents.ts` 的 `calcTotals`、`allocateOrderLine`、`sumAllocations` 與完結批次差額會在 `Decimal → Number → Math.round` 間轉換。尤其折扣按出貨比例分攤時，三次各出貨三分之一可能產生尾差。

處理方向：

- 金額全程使用 `Prisma.Decimal` 或整數最小貨幣單位。
- 明確決定稅額是逐行四捨五入或整張單據四捨五入。
- 最後一批出貨吸收分攤殘差，確保所有批次加總等於原單。

### 付款、退款與 POS

付款、退款、促銷、點數、現金班別與商城付款不得使用二進位浮點直接比較。所有「可退款餘額」「應收餘額」「找零」都要以相同 scale 比較。

## P1：固定精度

- 數量：固定 4 位小數。
- 單價：資料庫 4 位或依商業規則，計價後轉成貨幣 scale。
- 新台幣金額：目前規則為整數元；若未來支援外幣，需按幣別設定 scale。
- 稅率：不可用 `0.05` 類浮點直接累積，應保存百分比 Decimal。
- 傳票平衡：借貸雙方先轉同一貨幣 scale，再做精確相等，不使用 `0.001` 容忍值掩蓋錯誤。

## P2：報表與序列化

API 可在邊界把 Decimal 序列化成字串；前端只負責格式化，不再重新計算會計金額。Excel/PDF 匯出應從同一個金額服務取得結果。

## 必備回歸案例

- `0.1 + 0.2`
- 單價 0.1、數量 3
- 一張訂單分 3 次各出貨三分之一
- 折扣無法平均分配的最後一筆吸收尾差
- 含稅／未稅、逐行稅額與整單稅額
- 多次部分退款後不可超額退款
- 10,000 筆金額加總與資料庫 aggregate 完全一致

## 建議導入順序

1. 建立單一 `money.ts`，封裝 Decimal、scale 與 rounding mode。
2. 先替換文件總額、出貨分攤與傳票。
3. 再替換 POS／商城付款退款。
4. 最後替換報表與前端顯示。
5. 用雙算結果記錄差異一個版本，再正式切換。
